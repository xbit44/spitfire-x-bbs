Try custom displays on a test board

Use this sheet to check your own artwork before callers see it. Repeat the useful cases on your Windows and Linux test installations.

This is a hands-on checklist for 1.0.0b2, not a claim that every machine or artwork file has already passed. The Customization & Displays reference gives the exact names, fallbacks and limits.

Get ready

  1. Use a spare, stopped test board. Keep it separate from your live SFX installation and any real mail links. Back up the test board before changing files.
  2. Record SFX version, operating system, terminal/client, Telnet or SSH, ANSI/plain mode and caller security level. Use two ordinary test accounts with different levels and a separate authorized Sysop account. Use test credentials only.
  3. Save copies of every file you change. Use a small unique marker such as TEST MAIN LEVEL10 in each candidate. Keep artwork below its limits and in ASCII/CP437. Start the test BBS only when ready to connect.
  4. On Windows, use the menu preview first; it does not execute commands. Then make a real caller connection. On Linux, use the actual caller connection for artwork checks. Preview results alone do not check login order, command access, Door launch or update preservation.

Check login and optional screens

  • Use simple public text/values in SFPRELOG.ASC, generic NEWUSER and NEWREG, WELCOME1 and WELCOME3, and ALL. A normal interactive registration tries NEWUSER then NEWREG before the form. After successful login/registration, available welcome pages appear in numeric order, with the gap allowed, then ALL. Test both ANSI and plain fallbacks. Do not put caller-name codes in pre-account screens.
  • Use GOODBYE for a normal confirmed logoff, then try quick goodbye. The normal path shows the artwork; quick goodbye skips it.
  • Read SFNWSLTR in both graphics modes. Try the plain newsletter editor with a saved spare ASC file, then with an ANS edition present. The editor must protect that ANSI edition and leave both unchanged when it refuses.
  • On Windows only, check the configured inactivity ending and literal NONODES.ASC offline refusal where the test listener permits it. Keep refusal text below 4 KiB; confirm that @BBSNAME@ stays literal. Do not expect the Linux caller path to show these two custom event screens.
  • Do not count NEWUSER10, NONODES.ANS, CHATDONE or EVENTIME as live event checks. Their selector recognition does not supply a normal invocation in this build.

Check display codes and includes

In a copied normal menu, try @BBSNAME@, @BBSNAME|L20@, @TIMELEFT:HMS@, @@ and an ordinary email address. Values should fit their context; the width clips/pads as documented, the duration formats, one literal @ appears, and the email stays readable. Check a missing optional message/file value without assuming every menu supplies it.

Include a short HEADER.ASC from the same folder. Rename only that test header to check fallback; restore it afterwards. Test an invalid path include on a copied candidate. The parent candidate should be rejected rather than reading outside Display. Plain mode must not load an ANS include. Try a long page with normal paging and one explicit @PAUSE@; the caller should be able to continue without entering a menu command accidentally.

Check Door artwork and access

  1. Configure harmless test Door entries in a root, category and subcategory. Record their actual menu/Door IDs; do not assume they are 001 or 007.
  2. Give DOOR, the matching DRnnn and DPnnn files unique literal/public markers. Try the exact level suffix and generic ANSI/plain fallbacks. Stay within the three total menu levels.
  3. Select a Door through the menu. Its DP screen should precede launch; return should keep the launching menu path/page. An automatic logon/logoff Door should not show DP.
  4. Hide an entry from one ordinary test account. That caller should get the generated filtered menu. Type the hidden entry directly and confirm it cannot be launched. Change access during the test only through the normal configuration controls, then refresh.
  5. Keep @DOORNAME@ and other nonpublic codes out of DR/DP artwork: this build rejects those candidates. Do not treat artwork as a substitute for configured access.

Check the separate BotGate and chat files

If you use these features, test a valid and a deliberately unusable copy of bg-prelog.ans and confirm the built-in human challenge remains usable. In private chat, try pchat.ans at 80 by 24 or larger, then a plain/smaller terminal with pchat.asc. Keep the live title, conversation, input and control areas clear. Add one harmless emote of each mode and check the caller/target substitutions. These files do not run general @codes or includes.

Check an update and keep a useful result

  1. With the spare board stopped, save the bytes or SHA-256 of your custom generic and exact-level files, a custom include, a file with only one member of an ANSI/plain pair changed, and an unrelated personal display file. Keep their saved copies outside the installation.
  2. Use the normal matching-package Windows update/repair or Linux update. Keep your backup. Do not manually clear stock-file tracking.
  3. Compare those custom files with the saved originals. They should remain exact. Recognized stock files may be refreshed, and missing stock files may be restored. Repeat the short fallback/access check after updating.
  4. Record Pass, Fail or Not tried for each case, with the actual version/platform/client and a short observation. Keep original failures. If a picture helps explain a layout problem, save a small readable PNG and include the filename. Stop the test BBS and restore your original test artwork when finished.

A Windows result does not establish a Linux result, and preview does not establish a real caller result. Check the machine/client combinations you actually use and keep untried combinations clear when reporting a problem.
