What BinkD and SFX do

The setup uses ONE stock BinkD instance and ONE configuration profile for all your FTN networks. Each network has its own domain, addresses and outbound folder.

BinkD connects to other mailers, receives files, sends queued files and retries remote delivery. SFX processes the mail while the BBS is running. If BinkD remains running when you stop the BBS, it can still receive complete files. Its recorder saves the information SFX needs to check those files later. The recorder does not toss or scan mail, open the BBS database, or start the BBS.

Stopping SFX does not stop an independently running BinkD.

Choose the mailer

Stop SFX and the independent BinkD before changing mailers.

Windows SFXConfig: open FTN Networks. Under Mailer choose External binkd, set External binkd program to your stock BinkD executable (Browse... can select it), then choose Save Changes. Built-in SFX selects the Native mailer; Disabled stops SFX mail processing while keeping settings and mail.

Linux web Config: open FTN Networks, then Mailer Settings. Choose External BinkD under Mailer and enter External BinkD program. Choose Apply to Draft, then Save FTN Settings... and review the save. The other choices are Native SFX and Disabled - retain mail. Apply to Draft alone does not save settings.

The program field names stock BinkD, not SFXBinkD. Saving it does not start a program, generate a profile or install a BinkD service. External mode uses SFX for mail processing without a simultaneous Native listener or dialer.

Native listener endpoints and the setup wizard's hub host, port, session password, queued-mail contact and timer values do not control External mode. Their saved Native values remain for later use. BinkD uses the host, port, session password and calling rules in its own profile. SFX still uses separate packet, AreaFix and TIC passwords; do not clear them just because you changed mailers. Routes and Hold mail keep their rules.

Set Up a Network... opens the network setup steps. Supply the network and hub FTN identities, choose echoes and their permissions, then review before saving. In External mode the wizard does not supply BinkD's connection settings. Keep the manual shared profile consistent with the saved networks.

Place or update the optional helper

Use the helper supplied with the matching v1.0.0b2 test package; adding it alone does not update the Runtime or configuration programs. Install stock BinkD separately.

The Windows v1.0.0b2 test ZIP includes Optional/SFXBinkD/SFXBinkD.exe as an optional companion, with PLACEMENT-AND-BUILD.txt beside it. Place it manually at <SFX folder>\Bin\SFXBinkD.exe; Setup does not install this helper automatically. Stop independent BinkD before replacing it. If the file already exists, compare its checksum with the documented old/current helper. Do not overwrite an unknown file. Keep a recognized old copy separately until the update is checked. Preserve all FTN and Config data.

The fresh Linux v1.0.0b2 test package installs bin/sfxbinkd through its normal install/update path, with executable permission for the normal SFX owner. Keep access private to that owner, stop BinkD before updating it, and preserve ftn and config.

Prepare your profile

Create the source profile manually under FTN/External on Windows or ftn/external on fresh Linux. The helper does not create its password-bearing contents.

Use your normal Sysop account. On Windows, keep the FTN folder private with its existing SFX access permissions; do not prepare the profile as LocalSystem. On Linux, your account must own FTN with mode 0700 and the source profile with mode 0600. Use ordinary files and folders, not links.

The source profile and the generated run profile contain session passwords. Keep both private, including in backups. Do not paste them into chat or a support log, or put passwords on a command line. There is no second SFX session-password list to maintain.

Use supported profile reference to write the profile. Only its listed options are accepted. A general stock binkd.cfg may contain unsupported options. Do not add includes, receive commands, password files, or mail folders outside the board.

For each network, use its SFX network code in lowercase in the outbound path. Declare its domain and use domain-qualified local and remote FTN addresses. The companion reference lists the required fields.

Start from the SFX folder

Run the helper from the actual SFX board root. Relative paths start there, not in the profile's folder. Keep the helper under Bin on Windows or bin on Linux, and its profile/mail handoff folders under FTN/External or ftn/external, respectively. The board-root folder may contain spaces; the supported relative profile and spool paths cannot.

These are command forms, not commands to paste unchanged. Replace NETWORK, PROFILE and STOCK_BINKD_PATH with your values. Windows uses Bin\SFXBinkD.exe; fresh Linux uses ./bin/sfxbinkd. Never add a password argument.

Windows:

Bin/SFXBinkD --prepare NETWORK

Fresh Linux:

./bin/sfxbinkd --prepare NETWORK

Creates a network's handoff folders and marker. It does not write the source profile or supply passwords.

Windows:

Bin/SFXBinkD --prepare-run PROFILE

Fresh Linux:

./bin/sfxbinkd --prepare-run PROFILE

Checks an existing private source profile and creates a fixed copy for a new run, including its receive recorder command. It prints the run ID and generated configuration path. It does not start BinkD.

Windows:

Bin/SFXBinkD --launch PROFILE STOCK_BINKD_PATH [--server]

Fresh Linux:

./bin/sfxbinkd --launch PROFILE STOCK_BINKD_PATH [--server]

Checks the profile, creates a fixed run copy, then starts stock BinkD with that copy. Supply the BinkD executable path, not a shell command or extra arguments. Quote an executable path containing spaces.

Omit --server for normal combined operation: BinkD accepts incoming sessions and automatically calls out for queued mail. Add --server only when you want to accept incoming sessions without starting outgoing calls. The launcher does not install a service. Keep the launch session open; do not assume closing it leaves BinkD running.

Daily use and profile changes

Start the BBS when you want SFX to process waiting mail. BinkD can receive while SFX is stopped, but receiving a file does not mean SFX has imported it. In External mode, Scan requests SFX's outbound mail scan; it does not place a call. Poll is unavailable because BinkD handles outgoing connections. These actions require the BBS and mail processing to be ready. Disabled mode does not allow Scan.

A password-protected connection does not prove every address advertised by the other mailer. SFX still checks the file's network and link, separately from any configured packet or TIC checks. A known link without a BinkD session password can still need its configured packet or TIC password. A wrong or missing packet password leaves the packet held. A wrong or missing TIC password rejects the TIC; receiving the file successfully does not mean it was accepted into the file catalog.

BinkD uses the fixed profile created for its run. Editing your source profile does not change that running copy. Stop the old BinkD instance and launch a new run to apply a profile change.

Keep FTN/External/Runs on Windows or ftn/external/runs on Linux with pending mail. Its profiles and record files are needed to check which run received each file. Do not edit generated files, remove old runs just because a new one exists, or run the receive recorder by hand.

Handed to BinkD means SFX has saved the outgoing handoff. It does not mean Delivered. BinkD handles later retries and delivery. An empty queue or a missing spool file alone is not a delivery receipt. Recreating a handed-off job could send the same mail again.

One BinkD session can carry separate files for different networks. SFX checks each file against its network and link. A TIC may arrive before or after its payload; SFX needs both before adding the file to its catalog. LOCAL hatch uses an outgoing copy and preserves the source file.

Separate networks must use separate files, even when sent during the same session. A single bundle needing different network/link routes is unsupported: SFX keeps it intact and imports none of it. Keep the original and the reported reason for review. Do not rename or move it to force acceptance.

Private BinkD log

Each run writes its own diagnostic log:

Windows: FTN/External/Runs/<run>/binkd.log
Linux:   ftn/external/runs/<run>/binkd.log

The launcher prints the actual path. Use it privately when checking failed connections or retries. Stock BinkD may write a password sent during a failed login into this log. Keep its private file access unchanged: on Windows it is limited to the Sysop, SYSTEM and Administrators; on Linux the log is mode 0600. Keep backups of it private too.

Do not copy this raw log into the SFX log viewer, support reports or chat. It is separate from the SFX activity log. The helper sets loglevel 4 and conlog 0, so stock diagnostics go to this private file, not the console.

AreaFix, attachments and retained mail

AreaFix keeps its separate password check as well as any configured packet password check. Wrong or missing credentials do not gain access by arriving through BinkD. Generated replies are handed to BinkD; that status does not confirm their remote delivery.

The network's .MSG scanning option uses that network's selected directory. The existing scanner publishes attachment requests with Normal, Hold or Crash handling. This is not a new feature for turning every .MSG into a NetMail packet. Source .MSG and kill-sent attachment files remain without remote acknowledgement; restarting does not create duplicate jobs.

Existing processed-original retention now covers eligible completed External mail. SFX expires only the managed original after its normal identity, protection, completion and dependency checks pass. Held, partial, uncertain or still-needed originals remain. A Handed to BinkD label alone is insufficient; any required outgoing handoff must be durably committed.

Raw BinkD receive copies, run folders, indexes, consumed markers and handoff history are preserved separately. There is no new automatic cleanup for these files, even when SFX expires an eligible managed original. Allow for their disk use and check free space. Do not delete them to imitate retention settings; pending mail and recovery can depend on them.

If SFX reports a completed inbox file without usable receive-hook records, keep the file and its metadata for review. SFX does not invent a trusted receive record, import an incomplete download or remove that original.

Backup, restore and moving the board

Stop independently launched BinkD before restoring the board or doing FTN history recovery. If SFX reports that message ID history needs recovery, use Recover FTN History after the normal restore/preparation. Healthy complete-folder copies do not need that action merely because the computer changed; separate held items still need their own review.

Stop BOTH SFX and the independent BinkD instance before a full-folder backup, restore or transport-mode change. SFX Stop alone is not enough. Keep the whole board together, including the Windows FTN/External or Linux ftn/external source profiles, generated runs, receive records and outbound work.

After moving a board, use its normal platform preparation and update external launcher paths and any separately configured BinkD service working directory. Start from the new board root. Do not start two BinkD instances against the same handoff folders.

To stop using the optional helper, stop independent BinkD, settle or review pending mail, and select the desired mailer mode. Only then remove the recognized optional helper executable if desired. Keep the external FTN tree, board settings, spool and history. Windows uses FTN/External/Config; Linux uses ftn/external/config. This does not uninstall or manage stock BinkD.
